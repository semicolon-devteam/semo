# '주문이' 에이전트 E2E PoC — 결과 & 설계 교훈 (2026-06-09, 실 LLM)

**목적**: (B) 1차 "손/응대" 에이전트가 **가게 지식에 그라운딩**해 실제로 작동하는지, 외부계정 없이 실 LLM(gpt-4o-mini)로 검증. 동시에 E0 T0.2(추출을 시뮬→실 LLM) 확인.

## 핵심 결과: 실패(v1) → 수정(v2) — 값진 설계 교훈

### v1 — 관계(온톨로지)만 그라운딩 → ❌ 거짓 응답

- 실 LLM 추출 8건 → 임계 0.85 통과 2건뿐, 게다가 LLM이 `contains_item`(주문용 관계)으로 카탈로그를 잘못 매핑.
- 결과 그라운딩에 **소재·관리법·주문제작 가능 누락** → '주문이'가 _"주문제작은 진행하지 않습니다"_ 라고 **거짓 단정**. (실제론 가능) → 일반 챗봇 답보다 나빴음.
- **교훈 ①**: 가게 핵심 사실의 다수는 *엔티티-엔티티 관계*가 아니라 **속성/정책**(소재·관리법·배송·주문제작 여부)이다. 관계만으로 그라운딩하면 정보가 빈약해진다.
- **교훈 ②**: "그래프에 없으면 모른다고 하라" + **빈약한 그래프 = 거짓 부정**(없는 게 아니라 안 담긴 것을 "안 한다"로). 위험한 실패 모드.

### v2 — 그라운딩 = KB 프로필/정책 + 온톨로지 관계, 단정 금지 → ✅ 정확

- 그라운딩에 **가게 프로필(KB: 925실버·변색관리법·주문제작 가능·배송)** + 관계(온톨로지) 둘 다 주입. 누락 시 "확인 후 안내"로 지시.
- '주문이' 응답: 변색방지(천으로 닦아 보관) 정확 안내 + **주문제작 가능** 정정 + 가게명/소재 특정. 일반 챗봇("판매처에 문의하세요")보다 명백히 우월 → **차별점(해자) 실증**.

## 확정된 설계 규칙 (E0/E1 반영)

1. **그라운딩 = KB(속성·정책) + 온톨로지(관계)**. 관계 단독 금지. (속성은 KB, 관계는 entity_relations — 둘을 합쳐 컨텍스트)
2. **에이전트는 지식 밖을 단정하지 않는다** — 누락은 "확인 후 안내". (응대문구뿐 아니라 모든 모듈 공통 안전규칙)
3. 추출(T0.2)은 통제 어휘 강제 + **confidence 보정/few-shot 필요**(LLM이 관계 오매핑·과소확신 경향). 관계 enum에 카탈로그 관계(in_category/has_variant)가 contains_item과 혼동되지 않게 추출 프롬프트 가드.

## 입증 vs 잔여

- ✅ **입증(자율)**: 실 LLM 추출(T0.2) 동작 / '주문이' = KB+온톨로지 그라운딩 응대 에이전트로 **정확 작동** / 일반 챗봇 대비 우월 / tenant 격리·cleanup.
- ⏳ **잔여(외부/빌드)**: 추출 품질 향상(few-shot·검증), 넛지 UI(T0.3), `/my/knowledge` 라이브(T0.5), 그리고 **'주문이'를 라이브 런타임에 설치-작동**(serve-worker/Hermes dispatch + 게이트웨이 외부공개) = 게이트웨이 배포(외부) 의존.

## 산출물
